# Venue Estimated Costs

branch: claude/feature/venue-estimated-costs

## Summary

Every `Venue` should carry an estimated cost per adult and an estimated cost per child, so that itineraries can convey the likely expense of visiting each venue. These estimates are not looked up from a pricing API; they are generated by the LLM using contextual signals already present in the pipeline — the destination, and each venue's name, description, interest, notes, and tags. This gives trip planners a realistic, per-person cost signal for every venue without requiring a live pricing source.

## User Story

As a trip planner using the itinerary output, I want to see an estimated cost per adult and per child for each venue, so that I can gauge the overall cost of a day's plan and make informed decisions about which venues to keep or swap.

## Acceptance Criteria

- [ ] `Venue` has a new property representing the estimated cost per adult.
- [ ] `Venue` has a new property representing the estimated cost per child.
- [ ] Estimated costs are populated for every venue produced by the venue processing pipeline, using an LLM call that considers the destination along with the venue's name, description, interest, notes, and tags.
- [ ] The LLM-generated estimate reflects realistic, real-world pricing conventions for the destination (e.g. free/no-cost venues are estimated as zero, paid attractions reflect a plausible ticket price).
- [ ] Venues that are free to enter (e.g. public parks, viewpoints) are correctly estimated as zero cost rather than omitted or left blank.
- [ ] The two new properties are included in the itinerary output alongside the venue's existing details.
- [ ] If the LLM is unable to produce a confident estimate, the corresponding cost property is set to `null` rather than a guessed or placeholder numeric value.

## Scope

### In Scope

- Adding the two new estimated-cost properties to the `Venue` model.
- Generating both estimates via an LLM call as part of the existing venue processing pipeline, using destination plus the venue's name, description, interest, notes, and tags as input context.
- Ensuring every venue (regardless of interest type, origin, or status) that goes through processing receives both estimates.
- Surfacing the new properties wherever venue details are currently rendered or exposed downstream.

### Out of Scope

- Looking up real-time or authoritative pricing from external sources (e.g. ticketing sites, official venue pricing pages).
- Currency conversion or multi-currency support.
- Modeling group discounts, seasonal pricing, dynamic pricing, or age-tiered pricing beyond a single adult/child split.
- Estimating cost for meal venues (Breakfast/Lunch/Dinner) beyond whatever the standard estimation flow already produces for them, unless the user indicates otherwise.
- Any UI/front-end changes beyond what's needed to pass the new fields through existing output.

## UI / UX Notes

Not applicable — this is a data-layer change. The two new cost fields should be included wherever a `Venue`'s existing fields (e.g. description, hours of operation, duration) are already surfaced, so they appear consistently in any itinerary output or export without requiring separate UI work.

## Testing

- Unit tests verifying that the venue processing pipeline populates both cost fields for a representative venue.
- Unit tests covering the free-venue case (expect a zero estimate rather than a missing/null value).
- Unit tests covering the case where the LLM can't produce a confident estimate (expect `null` on the affected cost field(s), not a guessed numeric value).
- Unit tests confirming the estimation call is given the correct inputs (destination, name, description, interest, notes, tags).
- Regression check that existing venue processing tests continue to pass with the new fields present on every produced `Venue`.
