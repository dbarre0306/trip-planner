# Plan: Venue Status and Rejection Reason

spec: _specs/venue-status-rejection-reason.md

## Summary

Wire up the existing (currently unused) `status` and `rejection_reason` fields on `Venue` so they reflect real decisions made during venue processing. Per-venue checks (closed, no website) are decided while a venue is being built in `process_venue`, reusing the notes already fetched for that venue. Cross-venue duplicate detection — which needs the whole result set at once — runs as a second pass in `process_venues`, after all venues have been built, and resolves each duplicate group down to a single accepted "most specific" venue. Both the closed check and the duplicate/specificity judgment are delegated to the LLM via `chat_completion`, consistent with how this codebase already handles other fuzzy, judgment-based extraction (`venue_details.py`, `venue_url_selection.py`) rather than hand-rolling string-similarity or address-normalization logic.

## Assumptions

- Closed detection is folded into the existing `extract_venue_details` LLM call (which already reads the venue's notes) rather than issuing a second per-venue LLM call, since the spec says to rely on general-purpose judgment of the notes and the notes are already being sent to the model for detail extraction.
- Duplicate grouping, name/URL/address/geo_location matching, and "most specific" ranking are all resolved by a single LLM call per `process_venues` invocation, given the full list of venues (name, url, location, geo_location) — mirroring the existing `rank_urls` pattern of asking the model to sort/order candidates rather than writing bespoke fuzzy-matching or address-normalization code. This keeps duplicate detection tolerant of name spelling variation and address formatting differences without adding a new fuzzy-matching dependency.
- Duplicate grouping only considers venues that are still `"accepted"` after the closed/no-website checks — venues already rejected as `"closed"` or `"no website"` are filtered out before the grouping call and are never touched by duplicate resolution. Their own status/reason can't change (they're already rejected), and since duplicate matching is pairwise (name/URL/address/geo_location between two venues), an already-rejected venue never supplies information needed to link two *other* venues together. Excluding them also makes the spec's "cascading" case fall out for free: if the most specific real-world entry is closed, it's simply absent from the eligible pool, so the next-most-specific still-accepted duplicate naturally becomes the keeper without any special-casing.
- The LLM call for duplicate resolution returns each duplicate group (drawn only from the accepted-so-far venues) as an ordered list, most specific to least specific — the same shape `rank_urls` already uses for ordering candidates. The code accepts the first entry in that order as the keeper and rejects the rest of the group as `"duplicate"`. Per the spec's answer to the tie-break open question, if the model's response for a group doesn't distinguish an order (missing/invalid ranking), the code falls back to `random.choice` among that group's members.
- `Venue` (a non-frozen Pydantic model) is mutated in place to set `status`/`rejection_reason` rather than rebuilding new instances, matching the mutability already implied by the model having no `frozen` config.

## Files to Change

- `src/trip_planner/venue_details.py` — add a `closed: bool` field to `VenueDetails` (default `False`); extend `_EXTRACTION_INSTRUCTIONS` to ask the model to indicate, using only the notes, whether the venue appears to have closed; parse the new field out of the JSON response (default to `False` when notes are absent or the field is missing/invalid).
- `src/trip_planner/venue_processing.py` — in `process_venue`, after extracting `details`, determine the venue's own status: `"rejected"`/`"closed"` if `details.closed`, else `"rejected"`/`"no website"` if `lookup_result.url` is falsy, else `"accepted"`/`None`; pass these into the `Venue(...)` construction. In `process_venues`, after collecting `venues` from the futures, call the new duplicate-resolution step (from `venue_deduplication.py`) on the full list before returning it.
- `src/trip_planner/venue_deduplication.py` — new module. Exposes `resolve_duplicate_venues(venues: list[Venue]) -> list[Venue]`:
  - Builds a prompt listing every venue with an identifier, name, url, location (address), and geo_location, asking the model to group entries that describe the same real-world place (regardless of `interest`), matching on near-identical name, matching URL, and/or matching address/geo_location (tolerating formatting differences), and to order each group from most to least specific (e.g. a specific business kept ahead of the general property it's inside).
  - Parses/validates the response defensively (unknown identifiers, out-of-range groups, or single-member "groups" are discarded), following the same JSON-parsing and validation style already used in `venue_url_selection.py`.
  - For each valid group, walks the ordered identifiers to find the first venue whose `status` is still `"accepted"`; that venue stays accepted. Every other venue in the group that is still `"accepted"` is set to `"rejected"` / `"duplicate"`. Venues already rejected as `"closed"` or `"no website"` are left untouched. If the model returns a group without a usable order, falls back to `random.choice` among that group's currently-accepted members to pick the keeper.
  - Returns the same list with venues mutated in place (also acceptable to return a new list — either way, order and length must be unchanged, and errors during the LLM call/parse should not raise, mirroring the fail-soft behavior of `rank_urls`/`extract_venue_details`, i.e. leave venues as `"accepted"` if duplicate resolution can't be determined).
- `tests/test_venue_details.py` — add cases: notes indicating a closure produce `closed=True`; notes with no closure indication produce `closed=False`; no notes produce `closed=False` (default `VenueDetails()`).
- `tests/test_venue_processing.py` — add cases: `details.closed=True` yields `status="rejected"`, `rejection_reason="closed"` regardless of URL presence; a missing URL (with `closed=False`) yields `status="rejected"`, `rejection_reason="no website"`; a venue with notes-derived closed=False and a URL stays `"accepted"`/`None` (already partly covered by the existing default-case assertions). Add/update a `process_venues` test confirming the duplicate-resolution step is invoked on the full assembled list (e.g. patch `resolve_duplicate_venues` and assert it's called once with the venues list, and that its return value is what's returned to the caller).
- `tests/test_venue_deduplication.py` — new test file covering: name-similarity duplicates, URL-match duplicates, address-match duplicates (with formatting differences), geo_location-match duplicates, cross-interest duplicates, specificity resolution (hotel vs. restaurant example), cascading fallback when the most specific member is closed/no-website, reason precedence (closed/no-website preserved over duplicate), multi-way (3+) duplicate groups resolving to exactly one accepted venue, and the random tie-break fallback when the model doesn't provide a usable order. Follows the existing test style of mocking `chat_completion` at the module's import path (as done in `test_venue_details.py`/existing URL-ranking tests) rather than hitting the real OpenAI client.

## Implementation Steps

1. Extend `VenueDetails` and the extraction prompt/parsing in `venue_details.py` to produce a `closed: bool`, defaulting to `False` whenever notes are empty or the model's response doesn't include a usable value.
2. Update `process_venue` in `venue_processing.py` to compute `status`/`rejection_reason` from `details.closed` and `lookup_result.url` (closed check first, then no-url check, else accepted) and pass them into the constructed `Venue`.
3. Create `venue_deduplication.py` with the duplicate-grouping prompt builder, response parser/validator, and `resolve_duplicate_venues` orchestration described above, including the eligible-member walk and the random fallback for unresolved ordering.
4. Wire `resolve_duplicate_venues` into `process_venues` in `venue_processing.py`, applied to the full list of successfully-built venues before it's returned alongside `errors`.
5. Add/update unit tests in `test_venue_details.py`, `test_venue_processing.py`, and the new `test_venue_deduplication.py`, covering every scenario listed in the spec's Testing section.
6. Run the full test suite (`uv run pytest`) and fix any regressions.

## Testing

Matches the spec's Testing section directly:
- `test_venue_details.py`: closed detection from notes, and default `closed=False` with/without notes.
- `test_venue_processing.py`: per-venue status assignment for the closed and no-website cases, precedence between them (closed wins even without a URL), and confirmation that `process_venues` runs the duplicate-resolution pass over the complete venue list.
- `test_venue_deduplication.py`: duplicate detection by name/URL/address/geo_location, cross-interest duplicates, specificity-based resolution (including the hotel/restaurant example from the spec), cascading fallback to the next-most-specific eligible venue when the top pick is closed/no-website, reason precedence (closed/no-website preserved over "duplicate"), multi-way duplicate groups, and the random tie-break fallback.
- All new/changed tests mock `chat_completion` rather than making real API calls, consistent with the existing test suite.
- After implementation, run `uv run pytest` to confirm the full suite passes.

## Risks / Open Questions

- Folding "closed" detection into the existing `extract_venue_details` call changes that function's response contract (one more JSON key). Existing tests that assert on `VenueDetails` equality/fields will need the new `closed` field accounted for — should be additive and non-breaking if `closed` defaults to `False`, but worth double-checking no test does a strict full-object comparison that would break.
- A single LLM call handling grouping *and* specificity ranking for potentially many venues at once may hit prompt-size or accuracy limits as the venue list grows large; this plan follows the spec's guidance to rely on general-purpose model judgment rather than defining a size cap or chunking strategy, since the spec doesn't call for one.
- The spec says ties should be resolved "randomly," which is inherently non-deterministic; tests for the tie-break path should assert that *one* of the eligible venues ends up accepted and the rest rejected as duplicates (not a specific one), rather than asserting a fixed outcome.
